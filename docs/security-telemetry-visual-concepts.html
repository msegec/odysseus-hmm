Passive Safety Telemetry Concepts

These concepts preserve the current local-first, power-user model. The first pass observes what the app actually does, classifies it, and makes decisions visible before blocking or removing any behavior. Each claim is traceable to the flow that produced it, and each decision feeds a continual-improvement loop that hardens the project over time without losing features.

Concept 2: Event Detail Drawer

Each event should explain why it exists. This prevents generic "security alert" fatigue and gives the owner concrete evidence: request path, token state, command, file path, network target, and suggested follow-up.

Why this matters Most intended behavior here is powerful by design. The UI should distinguish expected power use from genuinely surprising behavior.

Concept 3: Provenance Deep-Dive

Every claim and log line must be answerable with one question: show me the exact flow that produced this. This view replays the path from trigger to classification, so a recorded event is reproducible evidence rather than an opinion.

Why this is the backbone Continual improvement depends on traceability. If we cannot replay why an event fired, we cannot safely codify a guardrail or a design fix from it.

Concept 5: Read-Only Container Posture Report

This complements event telemetry by showing the runtime surface: UID/GID, mounts, Docker socket exposure, capabilities, writable host paths, and sensitive environment variables. It is evidence, not remediation.

Why it belongs in phase one The app may intentionally have broad local access. A posture report makes that visible before choosing blacklist or whitelist controls.

Concept 6: Continual Improvement Ledger

Telemetry is only useful if observations turn into durable improvements. The ledger moves each finding through one fixed loop and records the result, so the project gets safer and cleaner over time without losing features.

Priority order Security first, new and improved features second, maintainability and UX QA/QC third. Every loop preserves existing behavior unless an explicit decision changes it.

A change ships only when the preserved behavior has a passing test or a recorded, explicit decision to change it.

Always Safe by design

Prefer owner checks, explicit privileges, route scopes, sanitized rendering, and allowlists over broad bans.

Prefer Modular boundaries

Each guardrail lives in one small unit with a clear interface, so it can be understood and tested on its own.

Prefer Traceable

Every codified fix links back to the provenance trace and forward to the regression test that locks it in.

Implementation Shape I Would Use

The visual concepts map cleanly to a small backend helper and one admin-facing report. This keeps progress valuable without touching enforcement paths first.

First PR goal Add passive telemetry plumbing, local storage, and a simple admin JSON/HTML report. No blocking.

1. Central event recorder

Add `security_events` storage plus `record_security_event(...)` with event type, source, user, route, method, classification, evidence, and local timestamp.

2. Low-risk instrumentation

Instrument token route access, generated reports, network targets, agent/tool actions, and container posture snapshots. Keep the instrumentation passive.

3. Admin report surface

Expose a read-only local admin report with filters for expected, needs-decision, dangerous, unknown, and no-evidence-found events.

4. Provenance in the schema

Store each event with its raw signals, the rule and rule version that classified it, a confidence score, and code references, so any claim can be replayed and stays interpretable after rules change.

5. Improvement ledger

Add a ledger that links a trace to its decision and to the regression test that locks the fix in. Order work security first, features second, maintainability/UX third, and never ship a change that drops a feature without an explicit recorded decision.

Design note: these are concept mockups only. The first pass intentionally avoids changing app behavior, auth policy, sanitization, SSRF rules, shell access, MCP access, local model access, or internal service access. Its long-term aim is continual improvement: traceable evidence feeding a fixed observe–decide–codify–verify–preserve loop that hardens security by design while keeping every feature.
